# Prototype Instructions

Run the local server yourself and open the preview in the browser available to this environment. Do not give the user server-start instructions when you can run it.

Before making substantial visual changes, use the Product Design plugin's `get-context` skill when the visual source is unclear or no longer matches the current goal. When the user gives durable prototype-specific design feedback, preferences, or decisions, record them in `AGENTS.md`.

When implementing from a selected generated mock, treat that image as the source of truth for layout, component anatomy, density, spacing, color, typography, visible content, and hierarchy.

- The 2D and 3D graph are camera/layout variants of the same R3F `GraphScene`: instanced nodes, batched edge buffers, a bounded offline Canvas2D label atlas, and Worker-owned Graphology/d3-force positions. High-frequency positions, pointer coordinates, clock values, and uniforms stay in refs/TypedArrays rather than React state.
- Graph appearance is a first-class, Obsidian-style user preference shared by the passive desktop graph and the interactive graph. Keep named presets plus bounded controls for node prominence/palette, relation opacity/color, sparse labels, layout forces, star field, Bloom, and quality; persist only versioned visual intent, keep effective device caps separate, and make the default profile visibly node-led rather than line-led. The default Nebula profile is 3D and carries the neural orb's theme-owned emission language: bright local node cores, alpha-composited relation energy to prevent dense-link overexposure, restrained moving signals, and Bloom derived from semantic theme colors.
- The desktop knowledge graph always renders at the selected profile's normal brightness. Never fade, filter, darken, or cover the graph to reduce distraction; user-owned graph controls reduce node/relation/label/star quantity or disable graph rendering instead.
- Start, Quick Settings, Quick Search, Alt+Tab, and other modeless menus never darken or blur the desktop. Their full-screen click-catcher stays visually transparent while the menu surface reveals and collapses from its taskbar or trigger anchor in 100–180ms; reduced motion removes spatial travel without hiding state.
- Keep the R3F runtime demand-driven and dynamically loaded. Static, hidden, reduced-motion, and settled scenes stop submitting frames; context loss, DPR, quality tiers, resource disposal, and deterministic non-WebGL fallback are shared runtime responsibilities.
- The independent global visual-effects root remains a lightweight DOM CSS overlay for scanline, grain, or vignette treatment that must cover functional DOM. It is not a second shader pipeline. A treatment that applies only to GPU content belongs in the single `CoreVisualCanvas` composer and must not be enabled in both places.
- Maximized managed windows and the single-Explorer docked state have no outer window outline or shadow. Let the global top rail, taskbar, and workspace insets define the frame; retain the window's internal toolbar, list, seam, selection, and focus lines.
- Maximized and docked managed windows must touch the exact inner edges of the global rails with no legacy floating-window gutter. Read the current `--top-height` and `--taskbar-height` tokens for window geometry so compact-height media rules remain synchronized; floating defaults may stay centered and smaller.
- Do not place isolated decorative cap lines on managed-window perimeters. In particular, the Terminal has no short top-left or bottom-right pseudo-element strokes; use only continuous structural dividers and semantic theme-accent state markers.
- The left side belongs to Windows desktop shortcuts; system telemetry belongs on the right.
- The desktop rail exposes at most six fixed shortcut slots at every formal release viewport. Remaining desktop entries stay in the full data model and remain discoverable through Start and Quick Search. Label length must never shift an icon's horizontal or vertical coordinate; labels wrap inside the tile, clamp to two lines, and end with an ellipsis when they exceed the tile bounds.
- Keep native File Explorer closed in the default desktop state.
- Keep persistent desktop rails, taskbar geometry, managed-window bounds, Explorer ledgers, and the graph canvas square or hairline-divided. Agent messages, composers, and transient popovers use the implemented radius vocabulary of 8px controls, 12px panels, and 10px message bubbles; context menus are the compact 10px/6px exception. Do not round every container. Glass, gradients, card stacks, chamfered chassis, neon fog, radar or ring motifs, and scanning effects are allowed as scoped HUD treatments, but they must improve hierarchy, remain source-truthful, and source every color from the active theme.
- JARVIS identity marks, ambient backgrounds, core state, and decorative geometry must be deterministic SVG/Canvas point-line vector work driven by CSS tokens. Do not use the older position-specific PNG crops in the runtime UI.
- Use Fluent UI line icons for functional commands. Windows-provided native application icons remain an explicit exception because they carry application identity; keep their surrounding geometry flat and tokenized.
- Keep emission local to active nodes, focus outlines, window edges, and live-state routes. Structural lines must remain legible on the active background; the theme accent communicates selection, connectivity, or active work while primary ink carries information.
- Remove legacy blue/cyan glow rather than recoloring every old halo with the default accent. Product-owned chrome, scrollbars, telemetry segments, focus rings, and status text use centralized neutral, accent, and semantic-state tokens; ANSI colors inside terminal content are the sole intentional component-owned color exception.
- All JARVIS-owned context menus use one compact command grammar across Desktop, Explorer, and Taskbar: theme-owned elevated surface, hairline, primary and muted inks, 10px menu radius, 6px item radius, one soft theme-owned shadow, and accent only for focus, selection, or checked state. Decorative instrument headers are omitted. Submenus inherit the same tokens; no private palette, glow caps, or ornamental glass.
- Reuse the canonical visuals indexed in `docs/design/README.md`; do not add retired color studies or one-off QA captures back to the repository.
- When the user explicitly asks to retain a new visual reference, use a lowercase kebab-case filename under `docs/design/references/` and update the reference index instead of creating another archive directory.

## Approved Windows runtime decisions

- Target Windows 10 and Windows 11 Home and Pro as the primary supported editions; Enterprise-only features are out of scope.
- Do not depend on Unbranded Boot, Custom Logon, Shell Launcher, Credential Provider replacement, Windows edition spoofing, or patched system DLLs.
- Keep `Explorer.exe`, native Windows sign-in, and recovery paths intact. JARVIS starts after sign-in as a reversible desktop host.
- The first native milestone is a WPF + WebView2 host with a browser-compatible mock adapter, real telemetry, real desktop-entry enumeration, `ShellExecute` launching, and a safe exit back to Windows.
- Desktop folders and the pinned File Explorer entry open the on-demand JARVIS File Explorer by default. Keep `Explorer.exe` available only as an explicit per-folder fallback. JARVIS File Explorer supports bounded create, rename, copy, same-drive move, verified cross-drive move, and Recycle Bin deletion behind explicit confirmation. Name conflicts auto-rename; a cross-drive move copies first and deletes the source only after byte and file-count verification. Permanent deletion remains disabled.
- Hybrid primary-taskbar composition is the default for fresh profiles: keep Explorer and its notification area running while JARVIS covers the remaining horizontal primary-taskbar region. Full replacement remains an explicit experimental opt-in; only that path arms an out-of-process watchdog, verifies the React taskbar renderer, and then hides `Shell_TrayWnd`. Any failed hybrid probe, exclusion, or renderer step falls back to the complete native taskbar.
- Restore the native primary taskbar on every normal exit, startup/render failure, watchdog failure, and host crash. Never hide secondary taskbars, edit taskbar registry settings, terminate Explorer, or alter the Windows work area in V1.
- `JARVIS_KEEP_NATIVE_TASKBAR=1` is the development and recovery-safe opt-out. If the native taskbar is not on the bottom edge, unavailable, or already hidden, keep it unchanged and skip replacement.
- The replacement taskbar must render all eligible running top-level applications, not only the four pinned launchers. Group windows by process for V1, use the Windows-provided application icon when available, show a window-count badge for grouped windows, and keep activate/minimize state synchronized with the native host.
- Ship Windows releases as clean self-contained `win-x64` packages with a per-user installer. Sign-in startup is optional, stored only in the current-user Run key, points at the currently installed executable with `--startup`, and must be controllable from the JARVIS Settings panel without administrator privileges.
- Keep release and recovery diagnostics on demand rather than in the telemetry loop. The native check must cover Explorer/taskbar recovery, WebView2, current-user install/startup registration, and `SHA256SUMS.txt` package integrity; a portable or development build must remain valid without an installer registration.
- Treat `JARVIS-update-manifest.json` as the future hosted-update metadata contract. Keep V1 on a manual update channel until signed packages and a trusted HTTPS release origin are available.
- Treat the V1 command surface as keyboard-first local quick search across approved applications, running windows, desktop entries, and Windows settings. Do not add a voice button, local speech-to-text pipeline, or a shared voice action router. Future voice control belongs to a separately integrated Codex/Claude-style computer-use agent and bypasses this local search executor.
- Keep local Quick Search inside the JARVIS desktop through the top rail and existing in-shell entry points; Pi owns the replacement taskbar's former Search slot. Do not register a system-wide search shortcut or create an independent hidden search renderer; the global `Ctrl+Shift+Q` recovery shortcut remains the only JARVIS-wide hotkey.
- Installed-application search indexes `.lnk` entries beneath the current-user and common Start Menu Programs roots plus packaged apps exposed by the Windows AppsFolder. Exclude uninstall/removal shortcuts. WebView receives opaque capability IDs; the host must revalidate shortcut roots or activate the host-cached AppUserModelID through `IApplicationActivationManager` with no arguments. Never expose an arbitrary shortcut path, AppUserModelID, or command-line launch method.
- The Start panel reuses the lazy cached application catalog: keep the stable pinned grid, expose a scroll-bounded grouped All Apps view, search installed apps and running windows locally, and store only the most recent opaque application capability IDs in versioned local storage after a successful launch.
- Start-panel pins and JARVIS taskbar pins share one versioned JARVIS registry. Persist only validated built-in IDs or opaque installed-application capability IDs, migrate the previous four-item order once, and resolve every entry against the current built-in/catalog allowlist before launch. This registry does not read or modify Windows native taskbar pins.
- Associate installed pins with live windows by normalized Shell Link target process names or the host-generated opaque packaged-application capability. Keep raw shortcut paths and AppUserModelIDs host-only, and consume matched windows so a running pinned app never appears again as a separate dynamic taskbar item.
- Refresh taskbar windows from out-of-context WinEvent hooks with short event coalescing, while retaining the one-second polling path as a recovery fallback. Event-only refreshes must not resample system telemetry or resend unchanged taskbar snapshots. Preserve first-seen ordering for unpinned running groups so foreground Z-order changes never make taskbar icons jump.
- In healthy full-taskbar mode, Alt+Tab and Alt+Shift+Tab use the bounded JARVIS HUD window switcher. Install its low-level keyboard hook on a dedicated message-loop thread, keep the callback free of enumeration/WebView/disk/synchronous UI work, and intercept only after the independent renderer is ready. Native/hybrid/safe modes, Ctrl+Alt+Tab, injected input, Win+Tab, secure desktop, and any failed first selection remain on the native Windows path.
- Match Windows taskbar input conventions where the safe launcher contract allows it: left click toggles the selected window, middle click or Shift+click launches another instance of a pinned item, and right click uses the native above-taskbar flyout for open/new-instance, close-group, and unpin actions. Never synthesize a launch target for an unpinned running process; context commands must resolve against the current renderer item before execution.
- The built-in Terminal launcher opens the JARVIS Terminal Workbench rather than `wt.exe`. Its renderer is lazy-loaded, while the native host owns allowlisted ConPTY sessions for PowerShell, CMD, and WSL; the renderer must never supply an executable path or command-line arguments.
- Visual themes are versioned whole-palette packs with centralized background, surface, card, text, border, accent, semantic-state, selection, elevation, graph-facing semantic values, and separate core/edge/halo/bloom emission layers. Support built-in switching and bounded user palette customization without arbitrary CSS injection. UI audio is synthesized locally, disabled by default, and user-controlled from Settings.
- Decorative screen effects are one optional desktop-wide subsystem with a versioned master switch and independently planned layers. Keep it mounted outside the functional React root, default it to Off, unmount disabled layers instead of setting their intensity to zero, and never pass Agent, terminal, Explorer, telemetry, taskbar, or workspace state into it. Semantic focus, selection, warning, and live-route emission remain part of the functional UI and must not disappear with decorative FX. Full-DOM bloom, ghosting, chromatic shift, curvature, or distortion require separately measured WebView2/host composition passes; do not simulate them with filters on `#root` or `.jarvis-shell`.
- Detailed process, hardware identity, graphics-adapter, and drive inspection is on demand. Never move those queries into the one-second telemetry loop. Temperature, fan, and voltage sensors remain visibly unavailable until a hardware provider and its license/runtime behavior are separately audited.
- The post-login boot sequence must reflect real runtime, telemetry, window-channel, and ConPTY checks. It remains skippable and must never imply replacement of Windows secure boot or sign-in screens.
