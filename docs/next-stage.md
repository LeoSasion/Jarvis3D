# 下一阶段：真实工作流验收

2026-10-02。当前已有本地配置回退、图谱搜索与邻域、显式摘录、会话恢复及参数比较。下一阶段建议以“能完成并重复验证一次真实工作”为目标，按以下顺序推进。

| 优先级 | 工作 | 完成标准 |
| --- | --- | --- |
| 1 | 打通真实 Agent 知识工作流 | 使用非敏感测试笔记和已配置的 Pi 服务商，完成搜索 → 两份摘录 → 比较/问答 → 核对来源 → 重启续聊；覆盖流式回答、取消、断连和重试，验证不会重复发送或悄悄附带旧正文。 |
| 2 | 建立可重复的真实 WebGL 回归 | 浏览器和 WebView2 使用完全相同的图数据、随机种子、镜头、质量与时间点；覆盖待机、2D、3D、冻结 A/B、退出重进及上下文恢复。记录截图、活动帧 P95、绘制调用和几何/纹理数量，区分帧间隔与 GPU 时间。 |
| 3 | 收敛一个可安装的候选版本 | 对指定提交重新执行打包、安装/升级/卸载、设置保留和原生恢复验证；补足 Win10、混合 DPI、多屏、锁屏和睡眠恢复的实机矩阵，逐项标记通过或仍缺设备。 |

第一项直接验证知识图谱与 Agent 的实际价值。现有验证确认了上下文和会话管线，但回答来自本地模拟器，尚不能证明真实服务商的回答质量及故障体验。开始前应确认选用服务商和现有认证可用。

在这条工作流中优先补两个小功能：点击回答中的 `[S1]` / `[S2]` 回看本次发送的摘录快照，以及导出附带来源路径和行号的 Markdown 答案。引用只解析为本次上下文中已有的来源，便于逐条核验结论。

第二项保护已认可的视觉：本轮功能测试曾依靠实际界面检查才发现冻结时材质时间滞后。当前浏览器与原生性能样本的关系数量也不同，只能作为各自基线；统一场景后，性能优化才有可靠的前后对照。

第三项将当前开发版本推进到日常使用。兼容范围与实际已测范围应分别记录，硬件不足的项目继续留在验收表中。
